# 健康档案稳定性与页面体验设计

## 目标

健康档案必须是用户可理解、可恢复的入口。网络或本地 API 暂不可用时，页面不能渲染成看似“没有信息”的空白档案；若用户已经完成建档，应优先展示本机保存的建档内容。

本轮处理“读取状态、档案概览页和编辑页本机保存恢复”。真实微信身份和云端同步属于后续独立任务，不能伪装为已经同步成功。

## 数据读取顺序

```text
进入健康档案页
  -> 请求 NestJS /health-profiles/me
     -> 成功：展示远端档案
     -> 失败：读取本机 onboarding 档案
        -> 有本地档案：展示本机档案，并明确标注当前状态
        -> 无本地档案：展示可重试空状态
```

`profile-loader.ts` 是唯一负责该决策的纯函数模块；页面不自行拼接本地字段或吞掉 API 异常。

编辑页保存时优先调用远端 API。远端成功后，如当前档案完整，会更新本机副本；远端失败时，只有身高、体重和健康目标都完整才允许保存到本机并提示“已保存到本机”。资料不完整时必须说明无法离线保存，不能显示成功提示。

## 页面结构

1. 使用 `AppNavBar` 提供稳定返回路径。
2. 加载中仅显示低对比度骨架，不显示虚假的数值或插画。
3. 有数据时依次显示身份摘要、档案完整度、身高/体重/BMI 三项指标、可编辑信息行和隐私说明。
4. 用户标识使用名称首字，不把序序头像冒充用户头像。
5. 本机数据状态使用一行轻提示和“重新连接”，不做重卡片、贴图或影响指标阅读的装饰。
6. 无数据状态只有原因说明和“重新加载”命令，避免用户误以为资料被删除。

## 视觉规则

- 信息区用分隔线与固定三列指标组织，不堆叠多张白色卡片。
- 主要内容使用浅绿灰、纸白与暖灰文字；不使用大面积深绿色操作条。
- 指标文字必须单行截断，三列固定宽度，避免长数值或标签撑破布局。
- 编辑入口始终是整行可点击区域，右侧使用仓库现有 `forward.svg`，不手绘图标。
- 页面不依赖新的图片资源；健康档案属于数据工具，不应使用与信息无关的角色插画填充空间。

## 验收条件

1. API 成功时，远端档案完整显示。
2. API 失败但本机存在建档数据时，显示本机档案和本机状态提示。
3. 两处均无档案时，显示“重新加载”状态，而不是空指标页。
4. 身高、体重、BMI、目标和基础资料均可进入对应编辑页。
5. `profile-loader.spec.ts` 覆盖远端失败回退和无数据状态；小程序类型检查、全量测试与微信构建通过。
6. `profile-save.spec.ts` 覆盖完整资料可生成本机副本，以及不完整资料被拒绝离线保存。
