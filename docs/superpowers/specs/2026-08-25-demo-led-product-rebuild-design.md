# 阶段 2B：Demo 驱动的正式端重构设计

**日期：** 2026-08-25  
**产品：** 和生序健康管理  
**状态：** 已确认，待用户审阅实施计划

## 背景与目标

阶段 2A 已交付真实的建档、计划、每日任务和四类健康记录，但正式端把这些能力呈现为偏通用的表单和卡片，未承接原型中已验证的治愈感、插画叙事和序序陪伴。

本阶段不复刻 Demo 的演示数据，而是用其体验结构承载正式端的真实数据。目标是让用户每天打开时先看到一件可完成的小事，理解其意义，并能在记录、计划、回顾中持续感到序序的陪伴。

## 范围和分段

### 2B-1：体验骨架重构

以当前 API、数据模型和插画资源为边界，重构正式小程序的视觉层级和交互节奏。

- **建档：** 恢复带 `hero.jpg` 的欢迎页和序序开场，但仍在建档前锁定 tab。保留实时 BMI、分类说明和非医疗提示；不增加当前档案模型无法保存的习惯字段。
- **首页：** 改为“今日陪伴”行动台。顶部使用 `home-companion-banner.png` 承载唯一优先行动；其后展示序序的上下文解释和最多三件可执行小事。记录状态改为轻量摘要入口，不再使用四张等权白卡。
- **记录：** 先选场景，再展开对应轻量表单。空状态使用 `record-desk-banner.png`；缺失关键记录时使用 `xuxu-record-reminder.png`。保存成功后显示与真实记录类型匹配的事实反馈，不生成评分或结论。
- **计划：** 以已有的体重/睡眠计划和任务为真实来源，用 `program-weight.png`、`program-sleep.png` 建立计划情境。任务完成时使用 `xuxu-complete.png`，未完成时保持中性、不施加压力。
- **序序：** 保留底部中央入口，同时以嵌入式陪伴模块出现在首页行动、记录成功、计划完成和后续回顾中。2B-1 的序序只解释已有数据和下一步操作，不提供自由聊天或医学判断。
- **我的：** 保持克制，聚焦健康档案、计划调整、提醒占位和数据管理入口，不制造未实现能力。

### 2B-2：真实回顾与调整

在 2B-1 的体验骨架稳定后，为当前记录模型增加可复现的读取和展示能力。

- 新增趋势读取：体重按日期聚合；睡眠、活动、饮食结构按周聚合；任何缺少足够样本的数据只显示记录提示。
- 新增周回顾：以本周和上周的可追溯事实为输入，输出“已完成”“可留意”“下一小步”三个区块。不得生成健康分、医学诊断、热量估算或无数据的趋势线。
- 新增计划调整：用户可在周回顾后修改当前计划方向和目标；调整会继续使用已有计划归档规则，历史记录不会被覆盖。
- 数据页使用 Demo 的回顾信息层级和未来 `insight-report-banner` 视觉方向，但图表、说明和建议均由真实 API 返回的数据驱动。

## 体验和素材规则

| 素材 | 正式用途 | 禁止用途 |
| --- | --- | --- |
| `hero.jpg` | 建档欢迎与序序开场 | 已建档后的重复装饰 |
| `home-companion-banner.png` | 首页唯一行动情境 | 普通卡片背景填充 |
| `record-desk-banner.png` | 首次记录、记录空状态 | 已有记录时的重复横幅 |
| `xuxu-record-reminder.png` | 缺失关键记录的提醒 | 制造焦虑的催促 |
| `program-weight.png` / `program-sleep.png` | 计划选择、当前计划状态 | 与计划无关的通用封面 |
| `xuxu-complete.png` | 任务完成和周回顾肯定 | 未完成任务的压力提示 |
| `xuxu-avatar.jpg` | 中央导航、陪伴身份、局部提示 | 代替用户头像或任意装饰 |

视觉遵循“少卡片、强情境、单主行动”：单页只有一个主要命令；插画必须承担状态或情境；按钮使用明确动作；底部五栏维持首页、记录、序序、计划、我的，并保留序序中央突出入口。

## 技术边界

2B-1 主要修改 `apps/mini` 的页面、组件、设计令牌和视图模型，不伪造后端字段。必要时允许从已有 `DailyHomeDto` 派生纯展示字段，但不把规则散落在页面组件中。

2B-2 在现有 NestJS 模块化单体中新增独立的 `health-insights` 模块和共享契约：controller 只处理身份与 DTO；service 组合记录和计划公开服务；repository 负责按用户和日期范围读取。聚合规则放在 `packages/domain` 的纯函数中并版本化，避免客户端和服务端出现两套计算结果。PostgreSQL/Prisma 仍是唯一事实源，CloudBase AI 不参与本阶段的趋势和周回顾生成。

数据流：`mini 页面 -> health-loop/insights service -> API DTO -> Nest insights service -> records/plans public service -> Prisma/PostgreSQL`。用户 ID 一律来自认证上下文，不从请求体接受。

## 错误、空数据与安全

- 加载失败：保留当前页面骨架，显示可理解的重试入口，不将错误伪装为“暂无数据”。
- 无记录或样本不足：明确说明还需要的最少记录量，并将用户引导到相应记录入口。
- 图表仅绘制有时间戳的真实记录；缺失日期可断开或说明，不做插值来营造趋势。
- 所有健康文字保持生活方式管理参考，不承诺结果，不替代医疗诊疗。

## 验收与测试

- 小程序建立完整视觉状态：建档锁定、无计划、无记录、部分记录、全部记录、任务完成、网络失败。
- 现有记录创建、版本化修改、任务完成和计划切换行为不回归。
- 2B-2 为聚合规则编写领域单测，为跨用户隔离、日期范围、样本不足和计划调整编写 API 端到端测试。
- 运行 mini 单测、Vue 类型检查、微信构建产物校验、API/领域测试、OpenAPI 生成及 CI 全量检查。

## 明确不在本阶段

- 自由 AI 聊天、模型调用、CloudBase AI 授权、AITrace 与风险支持。
- 食物库、热量计算、条码扫描、食物拍照识别、穿戴设备接入。
- 健康评分、医学诊断、未由真实数据支持的趋势或建议。

这些能力分别留给后续 AI 阶段和食物/设备能力阶段，并需先完成数据来源、授权、隐私和安全设计。
