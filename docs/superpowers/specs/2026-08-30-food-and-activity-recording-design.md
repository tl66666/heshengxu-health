# 食物库与运动记录体验设计

日期：2026-08-30  
范围：微信小程序中的食物库、早餐/午餐/晚餐/加餐记录、序序相机识别与运动记录。  
不包含：体重管理页面与体重趋势能力。

## 目标

围绕现有首页的五个记录入口，打通一条低摩擦的日常记录链路：用户可以从餐次进入食物库、搜索或拍照识别食物、确认份量并保存；识别过的食物可保存到“我的食物”，以后可像普通食物一样再次搜索。运动记录与饮食记录使用一致的选择、确认、保存节奏，并回写首页摘要。

成功标准：

- 用户从任意餐次进入后，30 秒内可以保存一条饮食记录。
- 拍照识别完成后，用户能确认候选、修改份量、选择是否保存到“我的食物”，并完成当前餐次记录。
- 用户可以在“我的食物”中再次搜索已保存食物，并保留图片与营养快照。
- 用户从运动入口选择项目、填写时长和强度后，三步内完成记录，首页显示运动时长与估算消耗。
- 视觉层级在小程序常见手机尺寸下稳定，图片不遮挡文字，不引入与页面语义无关的装饰。

## 产品结构

### 首页

保留现有首页导航和早餐、午餐、晚餐、加餐、运动五个入口。调整饮食热量摘要的层级：主数字展示已摄入，辅数字展示还可吃和运动消耗，使用细进度线表达当天状态。序序相机是唯一的主视觉横幅，文案为“拍一拍，认识这份食物”，点击进入识别页。

体重卡片保持原有职责，不新增入口、不改变数据接口，避免与体重管理任务产生边界冲突。

### 食物搜索与食物库

食物搜索页提供：

- 搜索框，支持中文名称与已有拼音搜索能力。
- 默认分组：常吃、食物库、我的食物。搜索结果显示名称、每 100g 热量、蛋白质和健康等级。
- 分类筛选沿用现有 `FoodCategory` 数据。
- 结果点击进入份量确认，不直接写入记录。
- 拍照入口作为次级但始终可见的操作入口，进入序序相机。

“我的食物”是用户确认保存后的个人数据集合。每条记录保留来源 `catalog`、`photo` 或 `manual`，图片地址、名称、营养字段、默认份量和创建时间。搜索时与公共食物目录合并，个人数据优先展示。

### 份量确认与入账

份量确认页统一处理搜索食物和识别候选：

- 顶部显示食物名称及来源（食物库/照片识别/我的食物）。
- 提供常用份量按钮和克数输入，两者相互同步。
- 仅展示热量、蛋白质、脂肪、碳水四项关键营养值；所有值按当前份量实时换算。
- 餐次选择为早餐、午餐、晚餐、加餐，默认使用首页传入的餐次。
- 保存操作调用现有 `meal-entries` 写入接口，成功后返回首页或餐次详情。
- 识别来源的食物额外提供“保存到我的食物”开关，保存个人食物成功后再写入餐次记录。

### 序序相机

流程为：选择/拍摄图片 → 上传 → 识别候选 → 用户确认候选与份量 → 选择餐次 → 保存记录。识别失败时保留图片，并提供“改用食物搜索”降级入口；网络失败时可返回搜索页继续记录。

相机页使用现有序序头像和 `home-companion-banner` 的水彩背景语言，图片预览区域保持真实比例，序序提示气泡只承担引导，不占主要操作空间。相机识别结果不自动入账，必须经过用户确认。

### 运动目录与记录

新增运动目录产品层，默认分类：步行、跑步、骑行、跳绳、力量训练、瑜伽、球类。热门列表显示运动名称、强度标签和每 30 分钟的估算消耗。

选择运动后进入轻量确认页：运动类型、强度、时长。消耗值由运动 MET、用户体重（若可用）和时长估算，页面明确标注“估算值”。没有可用体重时使用保守默认体重并显示提示，不阻塞记录。

保存复用现有 `activityRecords` 接口，新增字段（若后端合同允许）保存 `estimatedCalories`、`intensity` 和 `source: directory`；若后端暂不支持扩展字段，前端在记录快照中保留估算值，确保首页展示稳定。

运动页顶部使用 `record-desk-banner` 作为轻量横幅，插画靠右、文字靠左；列表与表单保持暖白背景和清晰分隔。只有缺少匹配运动画面时才调用 GPT Image 2 生成一张同水彩纸张质感的“人物锻炼、序序在旁边鼓励”横幅，并纳入静态资源，不在运行时生成。

## 数据与接口

### 复用的现有能力

- `food-catalog`：食物搜索、详情、分类、热门与推荐。
- `food-recognition`：上传、识别任务、候选结果、确认。
- `meal-entries`：餐次记录的创建、查询、更新、删除。
- `health-records` 的 activity 记录：运动记录的保存和当天查询。

### 新增的个人食物数据

建议新增 `user_foods`（或等价持久化集合）：

| 字段 | 说明 |
| --- | --- |
| `id` | 用户食物 ID |
| `userId` | 所属用户 |
| `name` | 用户确认后的名称 |
| `imageUrl` | 原始图片或压缩缩略图 |
| `source` | `catalog` / `photo` / `manual` |
| `energyKcal` | 每 100g 热量 |
| `proteinG` | 每 100g 蛋白质 |
| `fatG` | 每 100g 脂肪 |
| `carbohydrateG` | 每 100g 碳水 |
| `defaultServingLabel` | 默认份量名称 |
| `defaultServingGrams` | 默认份量克数 |
| `createdAt` | 创建时间 |
| `updatedAt` | 更新时间 |

接口最小集合：

- `GET /foods/search` 增加个人食物合并结果或提供 `scope=my` 查询。
- `POST /user-foods` 创建个人食物。
- `GET /user-foods` 查询个人食物，支持关键词。
- `DELETE /user-foods/:id` 删除个人食物。

## 视觉与交互规范

- 基础色沿用现有暖白、鼠尾草绿和少量珊瑚色；不新增紫色或高饱和渐变作为主色。
- 使用苹果式留白、细边框和克制阴影；不在页面中嵌套多层卡片。
- 现有插画资产按语义使用：`home-companion-banner` 用于相机入口，`record-desk-banner` 用于运动记录，食物相关空状态使用已有食物/序序插画。
- 图片作为横幅或空状态的一部分，文字区域保持可读留白；不把图片当作列表缩略图批量铺满页面。
- 主视觉图标和插画必须达到现有高质感序序素材的标准：有明确体积、材质细节、柔和投影和自然边缘，颜色与水彩纸张质感一致。禁止使用 emoji、系统 emoji、通用扁平贴图或未经统一处理的临时 SVG 作为相机/运动主图标。
- 运动和相机入口优先使用真实的成品位图资产；若现有素材不足，使用 GPT Image 2 生成后先做裁切、留白、透明边缘和小程序尺寸检查，再纳入静态资源。
- 所有主要操作使用图标+短文案，避免仅用符号表达关键动作；未知图标提供可理解的标签。
- 识别、上传、保存、失败、空结果均提供明确状态反馈，并保留继续操作的路径。

## 错误处理

- 食物搜索失败：显示“暂时无法连接食物库”，保留拍照和重试按钮。
- 识别失败：保留用户图片，提供重试和手动搜索两条路径。
- 识别候选不确定：要求用户选择，不自动入账。
- 个人食物保存失败：先提示保存失败，但不阻塞当前餐次记录；允许稍后重试保存。
- 运动估算缺少用户信息：使用默认值并显示“估算值”，不阻塞保存。
- API 写入成功但返回页失败：本地提示已保存，并提供回到首页按钮，避免重复提交。

## 测试策略

- 单元测试：份量换算、运动 MET 热量估算、来源合并排序、个人食物字段校验。
- 页面契约测试：首页五个入口路由、相机识别状态、确认页餐次与份量、运动目录和保存按钮。
- API 测试：个人食物创建/查询/删除、餐次记录写入、运动记录写入与当天聚合。
- 真机/构建验证：微信小程序构建、常见手机宽度下截图检查、弱网失败路径、重复点击防抖。

## 不在本轮范围

- 体重管理、体重趋势和目标设定。
- 社区、食谱推荐、营养师咨询。
- 运行时生成图片、视频或复杂运动动画。
