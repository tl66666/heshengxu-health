# 和生序阶段 1：建档闭环设计

**日期：** 2026-08-24  
**状态：** 已确认，进入实施

## 目标

让首次进入小程序的用户在 2 分钟内完成最小健康建档，并在完成前锁定正式业务入口。阶段 1 先验证体重管理闭环，同时保留睡眠、情绪、饮食和运动等目标选项，避免把产品做成只服务减脂的工具。

## 用户流程

```text
首次进入
  -> 基础资料（称呼、性别、出生日期可选）
  -> 身高与体重（BMI 实时计算与分级）
  -> 健康目标（减脂/维持/增肌/睡眠/精力/情绪）
  -> 画像确认
  -> 保存档案并解锁首页
```

未完成建档时只允许访问建档页；首页、记录、计划、AI 和“我的”不展示为可用入口，也不能通过路由或手动 URL 绕过。用户可以返回上一步修改，离开流程后恢复到最近一步。

## BMI 展示规则

身高单位为厘米，体重单位为千克。输入均为正数且在合理范围内时，客户端即时调用共享 `@heban/domain` 规则计算 BMI，并显示一位小数和分级：偏瘦（<18.5）、正常（18.5-23.9）、偏重（24.0-27.9）、肥胖（>=28.0）。这是健康管理提示，不作为医疗诊断；未填完整或输入无效时显示“填写身高和体重后查看”。

## 前端边界

- uni-app 只新增 onboarding 页面和本地表单状态，不在客户端保存 token 或 AI 密钥。
- 页面提交使用 API client；提交成功后刷新当前档案并跳转首页占位页。
- 表单控件提供清晰错误提示、下一步按钮禁用态和加载态。
- 阶段 1 不接入图片资产、真实微信登录、食物库、设备数据或真实 AI Provider。

## 服务端边界

- `HealthProfile` 增加受控的创建/更新接口，用户身份只从认证上下文取得。
- 请求 DTO 只接受当前步骤需要的字段，禁止传入 `userId` 或 `profileId`。
- 服务端重新校验身高、体重和目标枚举，并返回标准 API envelope 与 requestId。
- BMI 只由共享领域规则计算，不持久化为原始字段；响应可以返回派生 BMI 与分类。
- 当前阶段继续使用内存仓储；Prisma migration 单独作为后续基础设施任务，不阻塞页面流程开发。

## 验收标准

1. 新用户首次进入只能看到建档流程，其他页面不可点击且直接访问也被拦截。
2. 身高或体重变化时 BMI 数值和分级即时更新，边界值测试覆盖 18.5、24.0、28.0。
3. 无效输入不会提交，服务端拒绝越权字段和非法目标。
4. 建档成功后首页可访问，刷新后状态仍能从 API 恢复。
5. 前端单元测试、API 服务测试、e2e 和微信小程序构建全部通过。
