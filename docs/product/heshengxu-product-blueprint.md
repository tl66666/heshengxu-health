# 和生序产品蓝图

**版本：** 1.0
**日期：** 2026-08-25
**状态：** 已确认，作为后续产品与研发的唯一范围依据
**品牌主张：** 让健康回到自己的节律

## 1. 产品定位

和生序是一个微信小程序优先、可扩展至 App 的 AI 健康管理产品。它通过低摩擦记录、可执行计划、可解释回顾和受控 AI 陪伴，帮助用户把健康目标变成日常节律。

首个完整闭环服务减脂与体重管理人群，同时保留睡眠、情绪、肠胃与代谢等主题的扩展空间。和生序坚持自己的食物数据、陪伴方式和视觉系统，核心闭环是“目标 -> 记录 -> 行动 -> 回顾”。

产品提供健康管理与生活方式建议，不提供疾病诊断、处方、用药剂量、停药建议或替代线下诊疗的结论。

## 2. 用户与范围

### 2.1 首批用户

| 用户 | 当前需求 | 首批体验 |
| --- | --- | --- |
| 减脂与体重管理者 | 看见体重变化并形成可坚持的饮食、活动节律 | 完整目标、记录、计划与周回顾闭环 |
| 作息不规律者 | 了解睡眠是否稳定，减少补记负担 | 睡眠记录与节律任务，复用体重管理底座 |
| 有情绪、肠胃、代谢关切的用户 | 希望被产品理解，但需求尚未验证 | 建档中可表达关注主题；不展示半成品功能页 |

### 2.2 首批不做

- 食物百科、条码扫描、拍照识别、热量估算与营养处方。
- 社区、内容流、课程、商城、会员和广告触达。
- 穿戴设备接入、医院服务、检查解读和医疗问诊。
- 没有真实记录依据的健康总评分、虚构趋势或自动医学判断。
- 面向所有健康主题的复杂方案与自动调参。

## 3. 核心体验

```text
完成建档
  -> 设定或确认体重目标
  -> 首页看到今天最重要的一件事
  -> 快速记录体重、饮食结构、活动或睡眠
  -> 完成计划中的小行动
  -> 每周回顾自己的事实变化
```

首批要验证的不是用户能否浏览很多内容，而是用户能否完成连续 7 天的低负担记录与行动，并从回顾中理解自己的变化。

### 3.1 记录原则

- 每次进入记录页，用户在 10 秒左右能完成一条记录。
- 饮食先记录结构，不记录热量：主食、优质蛋白、蔬菜是否具备，以及可选的用餐时段与备注。
- 所有记录可补记、修改；历史报告基于版本化记录重新计算。
- 趋势与建议必须标明记录覆盖期；数据不足时明确说“暂不足以判断”。

## 4. 信息架构

底部使用五个固定入口，其中中间的序序是突出的品牌入口：

```text
首页 | 记录 | 序序 | 计划 | 我的
```

| 页面 | 回答的问题 | 首批内容 |
| --- | --- | --- |
| 首页 | 今天最值得做什么？ | 一条今日行动、四类记录进度、体重趋势摘要、周回顾入口 |
| 记录 | 今天发生了什么？ | 体重、饮食结构、活动时长、睡眠；补记、修改和当天时间线 |
| 序序 | 我想问什么、为什么要这样做？ | 安全聊天、快捷问题、授权数据摘要、计划和记录解释 |
| 计划 | 我正走向哪里？ | 主目标、周期、每日行动、本周完成情况、周回顾、调整入口 |
| 我的 | 我的资料和数据如何被使用？ | 档案、目标、提醒、AI 授权、隐私、导出与删除 |

“洞察 / 数据”不单独占底部标签。首页展示轻趋势，周回顾放在计划中，避免用户记录不足时面对空白的数据页面。

## 5. 序序 AI 陪伴系统

序序既是底部中间的主动聊天入口，也是一个有分寸的场景陪伴者。它的角色是看见、解释、提醒和支持，不替代页面功能或专业人员。

### 5.1 三层出现方式

1. **常驻入口：** 点击底部中间的序序进入聊天页。页面先说明能力与授权范围，再提供饮食、体重、活动、睡眠和计划的快捷问题。
2. **任务内陪伴：** 首页行动卡、计划任务和记录成功页使用 28-36px 小头像或一句话提示；点击后才展开“为什么建议这样做”。
3. **关键状态陪伴：** 完成建档、首次记录、连续完成、记录缺失和周回顾后提供短反馈。急症或高风险场景进入严肃的固定支持页，不使用鼓励性或玩笑式文案。

### 5.2 对话与授权

- 默认可提供一般健康教育与生活方式建议。
- 用户单独授权后，序序才可读取目标、计划、体重、饮食结构、活动和睡眠摘要。
- 用户可在“我的 - AI 授权”关闭个性化上下文；关闭后新对话不再使用这些数据。
- AI 写入计划、提醒或任何用户数据前必须展示草案并获得确认。
- 一日最多一次主动提醒；每条提醒可完成、延后、关闭或调整。

### 5.3 安全边界

急性危险症状、自伤或伤害他人风险、诊断、处方、药品剂量、停药与替代治疗请求必须被拦截。系统停止正常生成，展示固定求助话术和线下专业帮助路径，并记录最小必要的安全审计信息。

## 6. 功能模块与阶段

| 阶段 | 目标 | 内容 | 验收信号 |
| --- | --- | --- | --- |
| 阶段 0 | 工程底座 | uni-app、NestJS、PostgreSQL、质量门禁、AI 安全边界 | 已完成 |
| 阶段 0.5 | 档案持久化 | Prisma、健康档案、AI 审计最小模型 | 已完成 |
| 阶段 1 | 最小建档 | 四步建档、实时 BMI、目标选择、建档前路由锁定 | 已完成 |
| 阶段 2A | 每日健康闭环 | 首页、记录、体重目标、计划、睡眠共享记录、序序场景入口 | 已完成；验收见 `docs/engineering/stage-2a-acceptance.md` |
| 阶段 2B | 回顾与调整 | 可复现趋势、周回顾、计划调整、数据不足提示 | 用户能理解一周事实变化 |
| 阶段 2C | 受控 AI 对话 | 聊天页、授权上下文、草案确认、风险支持页与审计 | AI 建议可追溯、可撤回授权 |
| 阶段 3 | 多主题深化 | 情绪、肠胃、代谢主题逐个验证与扩展 | 每个主题有独立 PRD 与指标 |
| 阶段 4 | 运营与跨端 | 内容运营、通知、设备接入、App | 由真实需求决定，不预开发 |

阶段 2A 不接真实 AI Provider；序序先通过计划和记录状态提供规则化反馈。阶段 2C 才在服务端安全链路、授权、审核和审计均验收后开放真实对话。

阶段 2B-1 已先完成 Demo 驱动的正式端体验重构：建档欢迎、今日唯一行动、三件以内真实待办、场景化记录提示和计划完成状态均由现有档案、记录、计划和任务数据驱动。Demo 中的健康分、热量、趋势和自由聊天仍未开放。

阶段 2B-2 将在至少具备可追溯记录样本后实现真实趋势、周回顾与计划调整；样本不足时必须解释需要继续记录，而不是绘制补全趋势或生成结论。

## 7. 数据模型演进

现有 `User`、`ExternalIdentity`、`Consent`、`HealthProfile` 和 `AiTrace` 保持有效。阶段 2A 在此基础上增加以下领域对象，均按用户隔离、记录来源、时区、创建时间、更新时间与版本管理。

| 对象 | 核心字段 | 用途 |
| --- | --- | --- |
| HealthTarget | type、direction、targetWeightKg?、startDate、status | 用户当前主目标；体重目标允许仅选择方向 |
| WeightRecord | valueKg、measuredAt、note? | 体重事实记录；不可用 BMI 替代 |
| MealStructureRecord | mealType、hasStaple、hasProtein、hasVegetable、recordedAt、note? | 记录饮食结构，不产生热量结论 |
| ActivityRecord | activityType、durationMinutes、intensity?、recordedAt | 记录活动时长与类型 |
| SleepRecord | sleepAt?、wakeAt?、durationMinutes?、quality?、recordedAt | 支持简记和完整睡眠记录 |
| PersonalPlan | programType、startDate、status、ruleVersion | 当前执行的个人计划 |
| PlanTask | planId、scheduledFor、actionType、status、completedAt? | 每天的一件行动与完成情况 |
| WeeklyReview | periodStart、periodEnd、facts、ruleVersion、generatedAt | 仅保存可复现的事实摘要与规则版本 |
| AiConsent | scope、grantedAt、revokedAt? | AI 个性化上下文的独立授权 |
| Conversation / Message | phase 2C 定义 | 对话与用户确认的草案；遵循最小化保存策略 |

情绪、肠胃、代谢记录表暂不创建。对应主题被批准后，先写独立字段、风险和验收设计，再进入数据库迁移。

## 9. 工程边界

- 客户端：uni-app、Vue 3、TypeScript、Pinia；负责展示、输入校验、草稿与 API 调用。
- 服务端：NestJS 模块化单体；负责认证、授权、规则、持久化、AI 编排、审计与风险拦截。
- 数据：PostgreSQL 为事实记录来源；Redis、对象存储、通知和设备接入按后续需求单独引入。
- 契约：所有新 API 使用 `/api/v1`、统一响应 envelope、OpenAPI 与契约测试；纯规则位于 `@heban/domain`。
- 品牌与技术命名：对外产品名、文档和界面统一使用“和生序”；现有 `@heban/*` 包作用域、数据库开发名和历史迁移名属于内部技术标识，暂不重命名。
