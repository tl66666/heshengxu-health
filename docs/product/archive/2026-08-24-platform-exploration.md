# 和生序健康管理平台设计（历史探索）

**日期：** 2026-08-24
**状态：** 已确认，待评审
**产品定位：** 小程序优先、可扩展到 App 的个人健康管理平台

## 1. 目标与边界

和生序帮助用户建立健康档案、记录日常健康行为、理解变化趋势，并获得可执行的生活方式建议。首期面向多种健康目标，其中“减脂与体重管理”提供最完整闭环；睡眠与精力、压力与情绪、代谢风险管理、肠胃与生活方式同时提供最小可用闭环。品牌主张是“让健康回到自己的节律”，强调和身心、生息、循其序。

产品不提供疾病诊断、处方、用药剂量建议或替代线下就医的判断。任何急性危险症状、自伤风险、诊断和用药决策都必须触发风险分流，停止生成个性化医疗结论并提供清晰的求助引导。

首发端为微信小程序。产品架构必须允许在不重写业务规则、API 契约和数据模型的前提下扩展至 iOS 与 Android App。

## 2. 产品模型

采用“核心健康管理平台 + 目标化方案包”模型。

### 2.1 公共健康底座

所有用户可用，且所有方案包复用以下能力：

- **账户、身份与授权：** 微信登录、基础身份、隐私声明、健康信息授权、设备数据授权、AI 个性化授权和营销触达授权。
- **健康档案：** 基础信息、既往健康情况、用药信息、生活习惯、健康目标和风险提示。
- **健康记录：** 体重与围度、饮食、运动、睡眠、情绪、症状及用户主动录入的其他指标。
- **计划与行动：** 可执行任务、提醒、完成状态、计划调整和每周复盘。
- **趋势与洞察：** 历史趋势、阶段性变化、可解释指标、周报和异常提醒。
- **内容与 AI 助手：** 经审核的健康教育内容、基于授权上下文的解释、计划辅助和风险分流。

### 2.2 目标化方案包

方案包是围绕具体目标编排的记录、指标、内容、计划和洞察集合，不复制公共数据模型。

| 方案包 | 首期能力 | 首期深度 |
| --- | --- | --- |
| 减脂与体重管理 | 体重目标、能量预算、饮食与运动记录、体重趋势、平台期复盘 | 完整闭环 |
| 睡眠与精力 | 睡眠日记、作息目标、精力自评、微行动与周度趋势 | 最小闭环 |
| 压力与情绪 | 压力和情绪记录、舒缓任务、风险分流、趋势回顾 | 最小闭环 |
| 代谢风险管理 | 指标归档、饮食运动建议、检查提醒、生活方式趋势 | 最小闭环，不诊断 |
| 肠胃与生活方式 | 饮食耐受、排便和作息记录、生活方式建议 | 最小闭环 |

### 2.3 用户闭环

用户体验以“建档与目标 -> 每日记录 -> 建议与计划 -> 完成行动 -> 周度复盘”组织。首页只展示当日最重要的状态、任务、记录入口和提醒，避免成为所有能力的导航集合。

## 3. 首期信息架构

微信小程序底部一级导航为：首页、记录、计划、洞察、我的。AI 助手以全局浮层或首页入口提供，不占用单独一级标签。

| 一级页面 | 主要职责 | 关键二级页面 |
| --- | --- | --- |
| 首页 | 今日状态、待办、快捷记录、风险与提醒 | 今日详情、快捷记录、内容详情 |
| 记录 | 按时间添加、查看和更正健康记录 | 体重、饮食、运动、睡眠、情绪、症状记录 |
| 计划 | 目标、方案包、每日任务和周度回顾 | 方案详情、任务详情、计划调整、周复盘 |
| 洞察 | 趋势、指标解释、报告和提醒 | 体重趋势、睡眠趋势、周报、提醒详情 |
| 我的 | 健康档案、授权、数据导出与账户设置 | 档案、隐私与授权、通知、数据管理 |

## 4. 技术架构

### 4.1 技术选型

- **客户端：** uni-app、Vue 3、TypeScript、Pinia。以微信小程序为第一个发布目标，后续使用同一业务逻辑扩展 App。
- **服务端：** NestJS 模块化单体，REST API，OpenAPI 作为唯一接口契约。
- **数据：** PostgreSQL 保存事务和健康记录；Redis 用于缓存、限流、短期会话和异步任务协调；对象存储保存图片与导出文件。
- **数据访问：** Prisma 负责 schema、迁移和类型安全访问。复杂聚合通过经过评审的查询层实现。
- **异步与通知：** 初期使用 Redis 队列处理报告生成、提醒调度和内容索引；通知提供商由适配层隔离。
- **质量与交付：** pnpm workspace、Node.js LTS、ESLint、Prettier、Vitest、Playwright、GitHub Actions。

不在首期拆分微服务。模块化单体更适合当前领域演进和小团队协作；各模块通过明确接口、领域事件和独立数据访问层保持未来可拆分性。

### 4.2 系统边界

客户端负责页面展示、输入校验、本地草稿、缓存和调用 API，不保存服务端业务规则真相或敏感第三方密钥。服务端负责认证授权、规则计算、数据持久化、审计、AI 编排和第三方集成。

客户端、未来 App 和运营后台通过同一版本化 API 访问服务端。运营后台从第二阶段开始建设，不与小程序代码混放。

## 5. 数据模型与数据治理

### 5.1 核心实体

| 数据域 | 实体 | 说明 |
| --- | --- | --- |
| 身份与授权 | User、Identity、Consent、Device | 用户、登录身份、可撤回授权、设备绑定 |
| 健康档案 | HealthProfile、HealthCondition、Medication、HealthGoal | 档案、声明情况、用药、目标 |
| 健康记录 | MetricRecord、MealRecord、ActivityRecord、SleepRecord、MoodRecord、SymptomRecord | 原始事实记录，按类型拆分细节字段 |
| 计划与内容 | Program、Plan、PlanTask、Content、ContentVersion、Recommendation | 方案包、个人计划、任务、内容及建议 |
| 洞察 | HealthScore、Insight、WeeklyReport、Alert | 所有派生结果均可追溯计算规则 |
| AI 与审计 | Conversation、Message、AITrace、SafetyEvent、AuditLog | 会话、模型调用链、安全事件、操作审计 |

### 5.2 记录和派生数据规则

- 原始记录必须包含记录来源、记录时间、采集时间、单位、时区、创建者和版本。
- 用户更正记录时创建新版本或更正事件，不能静默覆盖影响既有报告的历史事实。
- BMI、热量、趋势、健康评分和周报属于派生数据，必须保存算法或规则版本、输入记录范围、生成时间和生成状态。
- 所有数值在 API 内使用标准单位；客户端只负责本地展示单位换算。
- 方案包对记录的解释通过规则配置或领域服务实现，不能在页面组件内计算。

### 5.3 隐私与权限

健康信息、设备数据、AI 个性化和营销触达为独立授权项。用户可在“我的 - 隐私与授权”撤回非必要授权。撤回后停止新的处理，并按数据保留策略处理历史数据。敏感数据读取、导出、删除和管理员查看必须记录审计日志。

## 6. AI 安全架构

AI 助手是受控编排服务，不是直接调用大模型的聊天界面。

请求处理顺序为：身份与授权校验 -> 风险识别 -> 最小化上下文组装 -> 检索审核内容 -> 模型调用 -> 输出校验 -> 保存 AITrace 和回复。

### 6.1 允许能力

- 提供经审核的健康教育和生活方式建议。
- 解释用户已授权的记录和趋势，并说明数据局限。
- 生成计划草案、提醒文案和记录建议，要求用户确认后才写入计划。
- 对回复标明建议依据或内容来源。

### 6.2 必须拦截的场景

- 急性危险症状、严重不适或紧急情况。
- 自伤、自杀、伤害他人等心理危机场景。
- 诊断、处方、药品剂量、停药或替代治疗决定。
- 数据不足、知识来源不足、用户无对应授权或输出无法通过安全校验的场景。

拦截后不得继续生成诊断性或处方性内容。系统展示固定安全话术、紧急服务和线下专业帮助建议，并记录 SafetyEvent；非紧急但不确定的问题引导用户咨询专业人士。

## 7. 仓库与文件规范

### 7.1 目标目录

```text
heban-health/
  apps/
    mini/                   # uni-app 微信小程序
    api/                    # NestJS API
    admin/                  # 运营后台，第二阶段开始
  packages/
    contracts/              # OpenAPI 生成类型、枚举、错误码
    domain/                 # 纯业务规则、指标计算、共享校验
    config/                 # 共享工具配置
    ui-mobile/              # 跨端 uni-app 组件
  docs/
    product/                # PRD、用户旅程、方案包规则
    architecture/           # ADR、数据模型、API、AI 安全
    engineering/            # 本地开发、发布、排障、规范
  prototypes/
    web-demo/               # 当前静态 Demo，迁移后保留为参考
  infra/                    # Docker、部署、监控和基础服务
```

当前 `index.html`、`styles.css`、`app.js` 和 `assets/` 是原型材料。实施第 0 阶段时移动到 `prototypes/web-demo/`；不在这些单文件中继续增加生产功能。

### 7.2 客户端文件规范

`apps/mini/src/pages/` 只放页面入口及小量页面编排。业务功能按 `src/features/<domain>/` 组织，每个域最多包含 `components/`、`composables/`、`services/`、`stores/`、`types.ts` 和 `constants.ts`。跨域组件进入 `packages/ui-mobile/`，不得将业务判断塞入通用组件。

页面、组件和组合式函数统一使用语义化命名：页面与组件用 PascalCase，组合式函数以 `use` 开头，服务文件以 `.service.ts` 结尾，状态文件以 `.store.ts` 结尾，测试文件以 `.spec.ts` 结尾。禁止使用 `utils.ts` 作为无边界的杂项文件。

### 7.3 服务端文件规范

服务端按 `src/modules/<domain>/` 组织。一个模块包含 controller、service、repository、dto、entities 或 schema、policy 和 tests。Controller 只处理 HTTP 协议与输入输出；Service 处理应用流程；Repository 负责持久化；纯指标和业务计算放入 `packages/domain/`。模块之间只能通过公开 service、事件或 contracts 交互，不能跨模块直接访问 repository。

### 7.4 接口、错误与配置规范

- API 路由采用 `/api/v1` 前缀，资源名使用复数 kebab-case。
- API 成功响应和错误响应使用统一 envelope；错误码在 `packages/contracts/` 定义并稳定维护。
- 每个新增或变更 API 同步更新 OpenAPI 文档和契约测试。客户端从契约生成类型，不手写重复 DTO。
- 数据库变更必须包含 Prisma migration、回滚或兼容策略、数据影响说明和测试。
- 运行配置只读取环境变量。仓库提交 `.env.example`，绝不提交真实 `.env`、令牌、数据库 URL 或第三方密钥。

### 7.5 测试、CI 与发布规范

- 领域规则、健康指标计算、风险识别和权限策略必须有单元测试。
- API 需要集成测试，验证认证、授权、输入校验、数据隔离与错误响应。
- 小程序关键路径至少覆盖建档、创建记录、任务完成、计划调整与风险分流的端到端测试。
- 每个 Pull Request 运行格式检查、静态检查、类型检查、单元测试、契约测试和受影响应用构建。
- `main` 分支受保护；发布使用版本号、变更说明、数据库迁移记录和可回滚构件。

## 8. 分期实施路线

### 阶段 0：蓝图和工程底座

建立 pnpm workspace、uni-app 和 NestJS 应用、PostgreSQL/Redis 本地环境、微信登录、鉴权、数据库迁移、统一日志、审计、OpenAPI、质量门禁和小程序发布通道。同步建立 AI 提供商适配层、风险拦截、输出校验、调用审计和安全配置，禁止客户端直连模型。将现有 Demo 迁入 `prototypes/web-demo/`，并从中提炼已确认的交互和视觉资产。

**完成条件：** 新开发者可按文档启动全套本地环境；CI 可以完成检查与构建；小程序可登录并调用受保护的健康档案 API；AI 调用必须经过风险与输出校验，并生成可查询的审计记录。

### 阶段 1：可用健康管理 MVP 与 AI 助手

完成档案、健康目标、体重/饮食/运动/睡眠/情绪记录、每日计划、趋势、周报和减脂方案包。交付 AI 健康助手：用户可围绕已授权的记录、计划和健康教育内容发起咨询；AI 提供生活方式解释、计划草案与记录建议，所有高风险请求均由安全策略拦截。其他四个方案包提供建档、最小记录、任务和趋势入口，但不承诺复杂个性化策略。

**完成条件：** 用户能从建档完成一个目标的 7 天记录与复盘；所有记录可更正且趋势可复现；非授权用户不能读取他人数据；AI 回复仅使用已授权上下文，包含非医疗提示，并能定位调用与安全策略结果。

### 阶段 2：多方案包与 AI 增强

补强睡眠、压力与情绪、代谢风险、肠胃方案包，建设审核内容库检索、方案包工具编排、来源引用、持续风险策略评估和 AITrace 审计运营能力。

**完成条件：** AI 只能在授权数据范围内工作；拦截场景有自动化测试；每条 AI 建议可定位模型、上下文版本和安全策略结果。

### 阶段 3：运营、增长与跨端

建设运营后台、内容管理、通知触达、设备接入、数据导出、A/B 实验和 App 发布。只有在性能、用户需求或独立部署需求明确时才拆分服务。

**完成条件：** 运营可不改代码地管理审核内容与方案配置；App 与小程序使用同一 API 契约；关键指标和故障有监控告警。

## 9. 已知风险与决策

- **跨端差异：** 首期只承诺微信小程序体验。封装平台能力，避免业务层直接调用微信专有 API；每个新增跨端依赖先做小范围验证。
- **健康合规风险：** 所有内容和 AI 输出遵守非医疗定位。上线前需由具备资质的专业人士完成内容和风险话术审阅。
- **数据质量风险：** 记录缺失和用户主观输入会影响洞察可靠性。洞察必须显示数据覆盖期与置信提示，不将相关性表达为因果。
- **范围膨胀：** 五个方案包首期共享同一核心数据与计划能力，只有减脂提供完整深度策略。新增复杂方案包必须先补充独立 PRD 和验收指标。

## 10. 下一步

本设计批准后，先编写阶段 0 的实施计划，并据此创建新工程骨架。阶段 1 至阶段 3 分别建立独立实施计划和验收清单，避免在一次开发中引入尚未验证的完整产品范围。
